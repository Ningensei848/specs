# 開発綱領 (constitution.md)

本ドキュメントは、「Copilotエージェント用カスタムプロンプトを改善するCopilotエージェント」のためのカスタムプロンプト開発における、絶対的な設計哲学、品質基準、テスト方針、およびエラーハンドリングの原則を定義する。以降の全フェーズにおける成果物は、本綱領に無条件で従わなければならない。

## 1. 設計・実装哲学

### 1.1 目的・文脈ファースト（Goal-Context Integration）

- ユーザーが作成したいプロンプトの「真の目的（Goal）」と「背後にある文脈（Context）」を鋭く洞察し、それを表現するための構造的な骨組みを瞬時に提供する。
- Microsoft 365 Copilotが提唱するプロンプトの4大要素（目的: Goal, 文脈: Context, ソース: Source, 期待値: Expectations）を極めて純粋な形で組み合わせる設計思想を貫く。

### 1.2 自己完結型知能（Air-gapped Adherence）

- 本システムは外部のインターネット情報から遮断されたイントラネット環境で動作するため、プロンプト内に「プロンプトエンジニアリングのベストプラクティス」や「Microsoft公式のコツ」を完全な静的コンテキストとして内包する。
- 外部APIやWeb検索に頼らず、与えられた入力と内包するルールのみから最高精度の改善案を自律的に導出する。

### 1.3 トークン効率の極大化

- 8,000文字という厳格な入力制限の枠内で最大の効果を発揮するため、冗長な説明を徹底的に排除し、記号やMarkdown構造、変数定義を駆使して意味密度（Semantic Density）を極限まで高める。

## 2. プロンプト品質基準

### 2.1 構造化とMarkdownの厳格運用

- 生成されるプロンプト、およびエージェント自身の内部インストラクションは、見出し、リスト、テーブル、コードブロックを用いて明確に構造化されていなければならない。
- 階層構造は一貫していなければならず、解釈の曖昧さを生む平文の長文記述を禁止する。

### 2.2 肯定指示（Positive Instructions）の原則

- エージェントに対する指示は、原則として「何をすべきか（Do）」を肯定文で記述する。「何をすべきでないか（Don't）」を記述せざるを得ない場合は、直後に「代わりにどのように振る舞うべきか（If-Then、代替手段）」を明記する。

### 2.3 プレースホルダーと変数の規格化

- ユーザーが編集すべき可変箇所は、一貫して `[可変項目名]` （半角角括弧）の表記で統一し、置換対象であることを一目で認識できるようにする。

## 3. 検証およびテスト基準

### 3.1 振る舞い駆動検証（Behavior-Driven Validation）

- 開発するプロンプトは、特定の入力パターン（Given）に対して、どのような思考プロセスを経て（When）、どのような形式・品質の改善プロンプトが出力されるべきか（Then）という受け入れ条件を明確に定義し、これを用いて検証する。

### 3.2 境界値・極端な入力値テスト

- 極めて短い入力（例：「メール要約のプロンプトを作って」など、目的のみが書かれた文）や、8,000文字に近い極めて冗長な入力が与えられた場合でも、システムが破綻せずに適切に動作することをテストシナリオとして保証する。

## 4. エラーハンドリング・セーフガード規約

### 4.1 入力不足時の自律的対話（Clarification Loop）

- ユーザーの要求に「目的」や「期待値」などの不可欠な要素が欠落している場合、システムは「推測による決め打ち」を極力避け、不足している要素について明確かつ答えやすいヒアリング（問いかけ）を実行する。

### 4.2 倫理と安全（Responsible AI）への準拠

- 生成・改善されるプロンプトは、Microsoftが提唱するResponsible AI原則（公平性、信頼性と安全性、プライバシーとセキュリティ、包括性、透明性、責任）を侵害する出力を誘発しないよう、ガードレールを内在させる。
