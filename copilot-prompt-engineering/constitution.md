# 開発憲章 (constitution.md)

## 1. 開発理念 (Development Philosophy)
本プロジェクトにおける唯一の最終成果物は、「Copilotエージェント用カスタムプロンプトを改善するCopilotエージェント」のためのカスタムプロンプト（Markdownテキストアセット）である。
本セッションで作成されるすべての周辺ドキュメント、中間仕様、および検証用アセットは、この最終プロンプトの品質（出力精度、トークン効率、表現の厳密性）を極限まで高めることのみを目的に作成される。
極限まで冗長性を排除した「高セマンティクス密度」を追求し、AIのコンテキスト消費を最小化しながら最大の自己最適化能力を引き出すことを最優先事項とする。

## 2. コア設計原則 (Core Principles)

### 2.1 宣言的表現の徹底 (Declarative Architecture)
プロンプトおよび仕様書から、手続き的な解説、情緒的修飾、曖昧な指示を徹底的に排除する。役割、制約、評価基準、および入出力関係のみを宣言的（Declarative）に定義する。

### 2.2 セマンティクス密度の定義 (Semantic Density Equation)
プロンプトにおけるセマンティクス密度 $D_{\text{semantic}}$ は、以下の数式モデルによって定義される。

$$D_{\text{semantic}} = \frac{E_{\text{entropy}}}{T_{\text{BPE}}}$$

ここで、
- $E_{\text{entropy}}$ はプロンプトが指示する制御ロジックおよび意味情報の有意味な複雑さ（情報量）を示す。
- $T_{\text{BPE}}$ は特定トークナイザ（例：o200k_base）によってエンコードされたプロンプトの実消費トークン数を示す。

本プロジェクトの目的は、最小の $T_{\text{BPE}}$ で最大の $E_{\text{entropy}}$ を発揮するプロンプトを構築することである。

### 2.3 直交性の維持 (Orthogonal Specification)
プロンプト開発を支援する周辺ドキュメント（.specify/ 配下のファイル群）は、互いに重複しない直交した役割を持ち、最終プロンプトの設計ソース（Single Source of Truth）として機能する。

## 3. プロンプトエンジニアリング・ガバナンス (Prompt Engineering Governance)
最終成果物であるカスタムプロンプト、およびそれを出力するメタプロンプトは、以下の GCESフレームワーク を厳格に内包し、曖昧さを排除しなければならない（MUST）。

### 3.1 GCESフレームワークの適用
プロンプト構造には、以下の4要素を明示的に組み込む。
- **Goal (目標):** プロンプト改善エージェントが達成すべき明確なゴール定義。
- **Context (文脈):** 改善対象のプロンプトが適用される環境、制約、およびBPE圧縮の必要性などの背景。
- **Expectations (期待値):** 改善後のプロンプトが満たすべき品質基準、フォーマット、および検証ロジック。
- **Source (ソース):** 改善の基準となる憲章やルール（本憲章のサブセットなど）の参照指示。

### 3.2 曖昧な表現の排除規約 (Strict Language Policy)
プロンプト内、および仕様書内において、AIの解釈に揺らぎを与える曖昧な助動詞や副詞（例：「〜すべき」「なるべく」「望ましい」）の使用を禁止する（MUST NOT）。
記述はすべて RFC 2119 に準拠した以下の厳格なキーワードで統一する。
- **MUST（必須） / MUST NOT（禁止）:** 強制される非交渉的なルール。
- **SHOULD（推奨） / SHOULD NOT（非推奨）:** 合理的な理由がない限り従うべきルール。
- **MAY（許容）:** オプション。

### 3.3 自己検証ロジックの内包 (Self-Verification Imperative)
最終成果物であるプロンプトは、出力された改善プロンプト自体が本憲章の「曖昧表現の排除」および「セマンティクス密度」を満たしているかを、メタエージェント自身が自己検証するプロセス（セルフ・フィードバック・ループ）を内包しなければならない（MUST）。

## 4. プロンプト最適化規約 (Prompt Optimization Standards)

### 4.1 BPE圧縮のためのテキスト最適化ルール
日本語のBPE分割効率を最大化（トークン消費の抑制）するため、プロンプトの記述時には以下を遵守する。
- **体言止め・命令文による圧縮:**
  - 「〜をすることができます」 $\rightarrow$ 「〜が可能（MUST）」
  - 「〜のようにしてください」 $\rightarrow$ 「〜を定義する（MUST）」
- **データ構造表現の最適化:** BPE分割率が高く、トークン消費の激しい「複雑な Markdown Table」の使用を禁止する。代わりに、リスト構造（Markdown List）または YAML ブロックを使用する。

### 4.2 禁止事項 (Anti-Patterns)
- **プレフィックス/サフィックスの許容:** 改善されたプロンプトを出力する際、"Here is the optimized prompt:" 等の無駄な挨拶や解説トークンを出力することを禁止する（MUST NOT）。純粋なMarkdownブロックのみを出力させる。
- **セマンティクス密度の低い冗長化:** 「丁寧な説明」を「厳密な指示」と勘違いし、トークン数を無駄に肥大化させるプロンプト設計を禁止する。
