# プロンプト仕様書 (spec.md)

## 1. プロンプト概要 (Prompt Overview)

本仕様書は、最終成果物である「Copilotエージェント用カスタムプロンプトを改善するCopilotエージェント」のためのカスタムプロンプト（以下、「メタプロンプト最適化エンジン」）が満たすべき機能要件、構造、および入出力振る舞いを定義する。

このプロンプトは、ユーザーから「未完成、または改善したいプロンプト」を入力として受け取り、`.specify/constitution.md` に定めるセマンティクス密度 $D_{\text{semantic}}$ の最大化、およびBPE圧縮ルールを適用した「極限まで洗練されたプロンプト」を自動的に出力する役割を持つ。

本設計は、仕様駆動開発（SDD）の標準フレームワークである `github/spec-kit` の考え方に準拠し、トークンマネジメントと評価設計において `microsoft/waza` を、頑健なエージェントスキル構築において `anthropics/skills` の構成思想を取り入れている。

---

## 2. ユースケース (Use Cases)

- **UC-1: プロンプトのリファクタリング (Prompt Refactoring)**
    ユーザーが記述した冗長なシステムプロンプトやカスタム指示書を入力し、指示の厳密性を損なうことなくトークン数を削減した高密度プロンプトを得る。
- **UC-2: 曖昧性の自己排除 (Ambiguity Elimination)**
    入力プロンプトに含まれる曖昧な表現（「〜すべき」「〜が望ましい」等）を検知し、RFC 2119に準拠した厳格な宣言的表現に自動変換する。
- **UC-3: BPEトークン圧縮 (BPE Compression)**
    日本語表現をトークン効率の良い表現（体言止め、英語ロジック、冗長な助詞の排除など）に最適化し、消費トークンを物理的に圧縮する。

---

## 3. 機能要件 (Functional Requirements)

### 3.1 入力パース機能 (Input Parsing)
メタプロンプトは、ユーザーから入力された「改善対象プロンプト」および「（任意で与えられる）ターゲットモデルや改善目標」を正確に認識・抽出できなければならない (**MUST**)。

### 3.2 構造分析およびリファクタリングエンジン
入力されたプロンプトに対して、以下の処理を自律的に実行するロジックをプロンプト内に組み込むこと。
- **セマンティクス解析**: 指示の本質的な「意味（エントロピー $E_{\text{entropy}}$）」を損なわないようコア要件を分解・抽出する。
- **GCES適合化**: 元のプロンプトに不足している要素（Goal, Context, Expectations, Source）を補完し、構造化する。
- **表現の厳密化**: 曖昧な命令表現をすべて「MUST / MUST NOT / SHOULD / MAY」に置き換える。
- **BPE圧縮**: 日本語特有の冗長表現を、高密度かつトークン効率の良い表現（英語ロジックと日本語コンテキストのハイブリッド）にリライトする。

### 3.3 自己検証およびユーザー主導修正ループ (User-Led Verification Loop)
メタプロンプトは、自身が生成した「改善後プロンプト草案」に対し、出力の末尾に自己評価スコアとチェックリストを可視化しなければならない (**MUST**)。

$$\text{Check: } T_{\text{actual\_draft}} < T_{\text{original}} \quad \land \quad \text{AmbiguityCount} = 0 \quad \land \quad \text{SemanticsRetained} = 100\%$$

この自己検証スコアをレポートとして出力し、ユーザーが納得いかない場合、即座にリトライを実行できるクイックフィードバック形式（`/retry [微調整の理由]`）を提案する (**MUST**)。

ターゲットモデルはデフォルトをGPT-5系クラス（`o200k_base` 相当以上）とし、ユーザーの指定に応じてClaude 4（`skills` 仕様）等へ動的に適合させる (**SHOULD**)。

## 4. インターフェース仕様 (Interface Specifications)

### 4.1 入力フォーマット (Input Format)
ユーザーは以下の形式で入力を提供する。

```markdown
# 改善対象プロンプト
[ここに改善したいプロンプトを記述]

# 制約・目標（オプション）
- ターゲットモデル: [例: gpt-5 / claude-4-8-opus]
- 圧縮目標: [例: トークン数 30% 削減 / 厳格な英語指示化]
```

### 4.2 出力フォーマット (Output Format)
余計な解説文（"Sure, here is..."等）を完全に排除し、即座にコピー＆ペースト可能な以下のMarkdownブロックのみを出力する (**MUST**)。

```markdown
# 改善後のカスタムプロンプト
[ここに最適化されたプロンプトコードを配置。GCES構造化、RFC 2119表現、BPE最適化済みのもの]

---
# 改善レポート（セマンティクス分析）
- 圧縮率: [元トークン数] -> [予測新トークン数] (約 XX% 削減)
- 適用した最適化:
  - [例: 曖昧表現 "should" を "MUST" に置換]
  - [例: MarkdownテーブルをYAMLリスト構造へ圧縮]

# 自己評価チェックリスト (Self-Evaluation)
- [x] セマンティクス（意味情報）の完全保持: 100%
- [x] 曖昧表現の完全排除 (RFC 2119遵守): 合格
- [x] ターゲットトークナイザー（GPT-5 / o200k_base等）への最適化率: 高

# 次のアクション (Retry & Refine)
プロンプトの特定の振る舞いを変更したい場合は、チャット欄に以下のように指示してください：
`/retry [具体的に修正したい内容や、セマンティクスが欠落している箇所をここに記述]`
```
